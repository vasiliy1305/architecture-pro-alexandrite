Задание 2. Мониторинг

1. Мотивация
Без мониторинга невозможно понять где теряются заказы, почему тормозит MES и как ведёт себя система под нагрузкой
Мониторинг позволит понимать 

мониторинг даст:
- прозрачность работы сервисов
- возможность быстро реагировать на сбои
- сокращение времени на поиск причин проблем
- удержание клиентов и партнеров

Бизнес ценность - мониторинг поможет количественно оценить качество сервисов, понять слабые места, понять актуальные запросы и недовольства клиентов \ заказчиков
построить метрики основанные на данных а не на интуитивных сображениях
Позволит собрать данные для анализа и развития бизнеса
в дальнейшем (после выявления слабых мест позволит принимать больше заказов масштабироватся и меньше терять заказы - а это реальные деньги)


2. Выбор подхода к мониторингу
Для API-сервисов (Shop API, CRM API, MES API) - RED (позволит оценить работу каждого сервиса, выявить проблемнве места на месте)
Для инфраструктуры (CPU, память, БД) - USE (особенно важен для MES сервиса так как он требует много ресурсов)
Для общей оценки - Четыре золотых сигнала (позволяет оценить целиком весь сервис - как температура или давление в медицине)

| Метрика                                    | Зачем нужна                                                 | Ярлыки              |
|--------------------------------------------|-------------------------------------------------------------|---------------------|
| RPS для MES API                            | Контроль нагрузки и выявление пиков                         | status, endpoint    |
| Response time для MES API                  | Выявление тормозов (особенно при расчете цены)              | endpoint, user_type |
| HTTP 500 для всех API                      | Отслеживание сбоев                                          | service, endpoint   |
| Number of dead-letter messages in Rabbit   | Выявление потерянных заказов                                | queue_name          |
| CPU % и Memory для MES API                 | Контроль ресурсов (C#сервис может съедать память)           | instance_id         |
| Number of DB connections (Shop, MES)       | Предотвращение исчерпания лимитов                           | db_name             |
| S3 storage size                            | Контроль расходов и роста данных                            |                     |
| RPS per user для Shop/CRM API              | выявление аномалий и DDOS                                   | service, user_type  |
| время ответа для Shop/CRM API              | выявление "медленных" запросов                              |  endpoint, user_type|
| CPU% для Shop/CRM API                      | выявление прожорливых сервисов                              |  instance_id        |
| «messages in flight» в RabbitMQ            | контроль активных не подтвержденных   сообщений             |queue_name            |


3. План действий
- развернуть Prometheus + Grafana (в облаке)
- интегрировать экспортеры метрик в Shop API, CRM API, MES API
- настроить экспорт метрик RabbitMQ через rabbitmq_prometheus plugin
- настроить дашборды по каждому сервису и общую панель "здоровье заказов"

настроить алерты на:
- RPS > 90% от пикового
- HTTP 5xx > 1% от общего трафика

Показатели насыщенности (Saturation)
- БД 80% макс подключений >>> алерт + авто-масштабирование
- MES API CPU > 70% или memory > 80% >>> алерт + ручной анализ
- RabbitMQ очередь > 100 сообщений >>> алерт + проверка потребителей

При превышении порогов
- мгновенное уведомление в Telegram
- автоматический тикет в Jira
- при повторном срабатывании >>> эскалация дежурному инженеру
