Задание 3. Трейсинг

1. Места где заказ может зависнуть 
- Shop API >>> MES API (загрузка 3D-модели и расчет стоимости) ?
- MES API >>> RabbitMQ (публикация события о завершении расчета)
- RabbitMQ >>> CRM API (прием и подтверждение заказа)
- MES API >> MES UI (назначение заказа оператору)

2. Данные которые должны попадать в трейсинг
- trace_id - уникальный идентификатор заказа-запроса
- span_id - этап обработки (расчет, публикация, прием и тд)
- order_id - ID заказа
- service_name - имя сервиса
- Время входа и выхода из этапа

3. Мотивация
Без трейсинга невозможно:
- понять где потерялся заказ
- диагностировать долгий расчeт стоимости
- определить дошeл ли статус до CRM

Метрики, которые улучшатся:
- время реакции на жалобы клиентов (с суток до 10ков минут)
- MTTR (Mean Time To Resolve) инцидентов
- доля зависших заказов (целевой - 0%)
- удовлетворtнность API партнtров (SLA по заказу < 1 ч)
- снижение нагрузки на поддержку (меньше ручных расследований)

4. Предлагаемое решение
- Технологии- OpenTelemetry (SDK + Collector) + Jaeger (UI + Storage)

Инструменты:
- в каждый сервис (Shop API, CRM API, MES API) внедряем OTel SDK
- заголовки traceparent передаются при HTTP-вызовах и в RabbitMQ (через заголовки сообщений)
- данные отправляются в Jaeger через OpenTelemetry Collector.

5. Компромиссы
- RabbitMQ не поддерживает контекст автоматически , нужно вручную копировать trace_id в заголовки сообщений
- MES (C#) требует интеграции OTel вручную, нет готового auto-instrumentation (в отличие от Java)
- Трейсинг не покрывает файлы в S3  но это не критично для отслеживания статусов заказа

6. Безопасность
- Jaeger UI доступен только внутри сети + защищен SSO
- Доступ имеют DevOps, бэкенд разработчики, поддержка
- Чувствительные данные (логины, email и тд) не включаются в трейсы
