Задание 5. Кеширование

1. Мотивация
Операторы MES жалуются, что страница со списком заказов загружается медленно, несмотря на пагинацию и фильтрацию. Это напрямую влияет на их мотивацию кто первым берет заказ тот получает оплату

Проблема вызвана тем, что каждый запрос списка заказов идет напрямую в MES DB, а запросы на чтение списка часто совпадают по пользователям и статусам

Цель кеширования
- Ускорить отображение списка новых заказов для операторов
- Снизить нагрузку на MES DB
- Улучшить UX и производительность MES UI

Объект кеширования
Список заказов (с фильтром по статусу и пагинацией), получаемый из MES API

2. Предлагаемое решение
Тип кеширования- Серверное (в MES API)

Почему не клиентское
- MES UI внутреннее SPA приложение, запускаемое на разных устройствах
- Клиентское кеширование не решает проблему первоначальной загрузки и не снижает нагрузку на БД

Паттерн кеширования Cache-Aside

Почему Cache-Aside
 - Подходит для read-heavy сценариев (операторы часто читают список)
- Простая реализация на стороне MES API (C#)
- При сбое Redis система продолжит работать 

Почему не другие паттерны
- Read-Through требует сложной настройки кеша как прокси, не нужен так как нет требований к прозрачности
- Refresh-Ahead  избыточен заказы появляются редко (до +100 в месяц), а не постоянно
- Write-Through/Write-Behind не нужны, так как запись списка заказов >> обновление статуса а это редкая операция и не касается кешируемого списка

3. Диаграмма последовательности
Оператор >> MES UI >> MES API >> [Кеш (Redis)] >> [(если промах) MES DB] >> ответ >> (кеш)


4. Стратегия инвалидации кеша
Программная инвалидация + по ключу + временная (TTL = 60 сек)

Программная при любом изменении статуса заказа 
По ключу можно очищать не весь кеш, а только затронутые статусы 
TTL как на всяки случай если инвалидация по каким-то причинам не сработала

TTL 60 сек все еще допускает показ устаревшего списка 
Чистка по событию дает максимальную актуальность
Защита от ошибок если событие пропущено TTL обеспечит обновление


Задание 5.
В качестве зоны кеширования выбран список заказов в MES, действительно проблемный участок с точки зрения нагрузки и UX пользователей. Принято решение о серверном кешировании на стороне MES API, а не в браузере, и это хорошо обосновано. Использование Redis как отдельного кеш-хранилища выглядит уместным для этого сценария. Прописан базовый сценарий чтения: запрос оператора -> MES UI -> MES API -> кеш -> БД.
Рекомендации: пересмотреть выбор паттерна кеширования. В текущем виде используется Cache-Aside, но для сценария, где статусы заказов меняются и через интерфейс, и через очередь, лучше подходит паттерн, при котором запись сразу попадает и в БД, и в кеш (например, write-through). Если вы хотите остаться на Cache-Aside, нужно подробно расписать, как гарантируется согласованность при всех изменениях статуса. Добавить описание сценариев изменения статуса: 1. оператор берёт заказ через MES UI; 2. статус меняется по событию из брокера. Для каждого сценария важно показать, как обновляются БД и кеш, и как это отражено на диаграмме последовательности. Переработать стратегию инвалидации: сделать основной опорой программную инвалидацию по событиям изменения статуса, а использование TTL оставить только как вторичный «страхующий» механизм, если он вообще нужен. Текущий акцент на TTL и инвалидации «по ключу» лучше ослабить и объяснить, как вы избегаете появления устаревших данных.
